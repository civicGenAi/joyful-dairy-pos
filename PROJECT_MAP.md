# PROJECT_MAP.md — African Joy Dairy POS

A complete map of the codebase as it stands today (Phase A of the completion mission). Generated before any UI changes have been made.

---

## 1. Stack (actual, as found)

> The brief in section 7 specifies "React + Vite + TypeScript, react-router-dom for routing. Do NOT introduce TanStack Router/Start". The actual repo is built on **TanStack Start + TanStack Router** (file-based routes, Nitro server, generated route tree). Per user direction, the stack stays as-is; the brief is treated as outdated on this single point.

- **Build:** Vite 7 (`vite dev`, `vite build`) with `@tanstack/router-plugin` and `@lovable.dev/vite-tanstack-config`.
- **Framework:** TanStack Start (`@tanstack/react-start`) + TanStack Router (`@tanstack/react-router`) with file-based routes and an auto-generated `routeTree.gen.ts`. Server entry: `src/server.ts`. Client entry: `src/start.ts`. App shell route: `src/routes/__root.tsx`. Nitro `3.0.260429-beta` is in devDeps.
- **UI:** React 19, Tailwind v4 (`@tailwindcss/vite`), shadcn/ui (full Radix surface in `src/components/ui/`), `lucide-react` icons, `framer-motion` for transitions / count-ups, `recharts` for graphs, `sonner` for toasts.
- **Forms/state:** `react-hook-form`, `zod`, `@tanstack/react-query` (provider mounted in `__root.tsx`; not used yet — all reads are direct mock imports).
- **Fonts:** Plus Jakarta Sans (display), Inter (body), JetBrains Mono (numbers) — loaded via Google Fonts from `__root.tsx`.

### How data is read today

Every screen does **direct named imports** from `@/mock/data`:

```ts
import { FARMERS, CUSTOMERS, STOCK, ... } from "@/mock/data";
```

Mutations stay in `useState` inside the screen (or just toast on save). There is **no repository/service layer** — Phase E will need to introduce one (`src/lib/data/*`) so each screen calls `farmers.list()`, `customers.recordDeposit()` etc.

## 5. App state (`src/app/context.tsx`)

`AppProvider` exposes:

- `user: User | null` — currently signed-in (in-memory only, lost on refresh).
- `role: Role` — active role (used by Sidebar/Topbar). Defaults to `admin`. Can be switched via the "View as role" dropdown.
- `lang: 'sw' | 'en'` — Swahili by default; toggled in Topbar/Login.
- `login(email)` — looks up by email, sets first role; falls back to USERS[0].
- `logout()`, `setRole()`, `setLang()`.
- `t(sw, en)` — inline translator.

**Limitations to note:**
- No durable persistence; refresh logs out.
- "View as role" mutates the live `role` but does not preserve the user's primary role separately, so a finance user looking "as" route can't trivially revert.
- No capability/permission map — RBAC is implicit via the nav list, not enforced on route mount.

## 6. Design system (current usage)

Defined in `src/styles.css`:

- **Tailwind v4** with `@theme inline` exposing brand tokens: `--color-brand-green-{900,700,500,300}`, `--color-brand-lime`, `--color-brand-red`, `--color-ink`, `--color-warning #E5A100`, `--color-info #1D9E75`.
- OKLCH-based light + dark themes (`.dark` exists but no toggle is wired).
- Brand gradient utility `.brand-gradient` and `.brand-gradient-text` (135° green-to-lime). Used heavily on hero panels, active nav, primary buttons, login left panel.
- Shadows: `--shadow-card`, `--shadow-elevated`.
- Pill utilities `.pill-success/.warning/.danger/.info/.slate`.
- `.table-zebra` for table striping.
- Custom scrollbar in brand greens.
- `.font-num` enables JetBrains Mono with tabular-nums for all numbers.

Card pattern across the app: rounded-2xl, `border border-border`, `shadow-card`, with a `<SectionCard>` providing the header.

Hero pattern: rounded-3xl, brand-green gradient, blurred circular accents (red and white blobs), white text.

**Things that look inconsistent or off-pattern:**
- Several gradient strings are hand-rolled instead of using the `brand-gradient` utility — e.g. `style={{ background: "linear-gradient(135deg, #1E7C3F, #8CC63F)" }}` is repeated dozens of times. A single shared `gradient: 'brand' | 'brand-soft'` prop on `Button` would cut hundreds of lines.
- A few screens still use the em-dash character in UI copy ("African Joy POS is under brief maintenance. We'll…"). The brief forbids em dashes in UI copy.
- Dark mode tokens exist but no toggle.
- The CustomersScreen tab filter uses a tricky ternary that mixes precedence (`tab !== "all" && tab === "overdue" ? ... : tab !== "all" && c.type !== tab`). Works but is fragile.

## 7. RBAC today

- Source of truth: `NAV_GROUPS_BY_ROLE` (in `mock/data.ts`).
- Sidebar renders only groups/items defined for `role`.
- Route components themselves do **no role guarding**. A user could navigate to `/settings` even if `sales`. Only `AppShell` redirects unauthenticated users (`if (!user) return <Navigate to="/" />`).
- Day-close on `/reconciliation` is the only operation gated on role (button is `disabled` unless `role === admin | production`).
- Multi-role users exist in mock (`peter`, `lightness`) but `role` state holds only one active role at a time — there is no "union of capabilities" logic per the brief.

## 9. Business flow — restated in our own words

1. **Procurement (morning + evening, every day).**
   - Women farmers deliver milk at one of two points: **Point A — Olasiti** (field) or **Main — Arusha** (plant).
   - The collector records the entry: farmer × date × session × litres × point × optional quality note. Rate per litre is the standard 1,200 TZS unless overridden.
   - This accrues an obligation to the farmer; nothing is paid yet. The system tracks a running `currentBalanceTZS` per farmer.

2. **Payment cycle (every 15 days).**
   - On the cycle date, Finance initiates payouts to farmers based on the litres collected during that window. The payout can be delayed if cash flow doesn't permit; the balance stays open and the farmer is shown as `delayed`.
   - Each payout reduces the balance; the next cycle starts from zero litres.

3. **Milk movement (intra-day).**
   - Milk can be transferred Field → Plant, Plant → Van, Field → Van. Each transfer moves litres between locations. Once in production, some milk gets *separated* into raw milk for fresh sale + cream for ghee + curd for cheese.

4. **Production.**
   - Production manager looks at raw milk on hand and the plan-to-produce. Records a batch: input litres → output kg/L/pcs, with a computed yield % and a wastage entry.
   - Finished goods land in **Finished stock**. Some go directly to **POS** (counter) and **Van** (route) for sale; some are issued to large orders (Mamis Bistro, CSR Hotel etc.).

5. **Sales channels.**
   - **Counter POS**: walk-in or named customer, three price tiers (own container / with bottle / bulk), cash / credit / M-Pesa / stock-issue. Generates a printable receipt.
   - **Route**: driver loads the van morning or evening, runs the route, records each sale (cash, credit, mpesa) along the way, records returns at the end, and does an end-of-day cash-up that produces a deposit receipt for finance.

6. **Customer types and credit.**
   - *Cash* — paid in full at sale, no statement.
   - *Per-sale credit ("Bill")* — recorded per transaction, paid off later.
   - *Monthly credit deposit customers* — draw products all month, deposit periodically; a monthly statement shows opening + takings − deposits = closing, with ageing (current / 30 / 60 / 90+).

7. **Consumables store ("Ghala").**
   - Packaging (Madumu, Vikopo, Trays, Boxes). Store keeper receives purchases, issues to production / route / POS. Reorder thresholds trigger alerts.

8. **Daily reconciliation & day-close.**
   - At the end of the day, per product, the conservation rule must hold:
     `Opening + Collected + Produced = SoldCash + SoldCredit + Separated + Spoilt + Returned + Closing`
   - When every row balances, the production manager (or admin) **locks the day**. The closing for each product becomes tomorrow's opening. Once locked, the day's numbers are read-only.

9. **Finance.**
   - Tracks receivables (customer credit) and payables (farmers). Records deposits (route cash-up, customer payments, counter banking). Confirms the production manager's day-close.

10. **Reports.**
    - Daily mirrors the team's paper sheet, per-product. Weekly / monthly / yearly add trends, totals, channel splits, top customers, spoilage and yield metrics. Delivered to Owner/Finance/Production via WhatsApp / Email / SMS on a schedule.

## 10. Inconsistencies and open questions surfaced during the survey

1. **Routing stack mismatches the brief** (handled — staying on TanStack per user choice).
2. **`react-query` is provided but not used.** Either remove (Phase E may want it back when wiring backend) or actually use it for repository calls in Phase E.
3. **No route-level role guards.** `/settings` is reachable by `sales` if they type the URL.
4. **Multi-role union not implemented.** A user with `["sales","store"]` only ever sees one role at a time.
5. **Day-close is local state in the screen.** Once "locked", refreshing un-locks. No mock persistence layer.
6. **Several gradients are hand-rolled** instead of using `brand-gradient` utility (low-priority cleanup).
7. **A few em-dash characters appear in user-facing copy** (`UtilityScreens` subtitles, JoyLogo subtitle uses `·` which is fine; the offline subtitle is fine; the maintenance subtitle has "We're upgrading the system" — fine; double-check `UtilityScreens` for `—`). Brief forbids em dashes.
8. **CustomersScreen tab filter logic is fragile** — works but the operator precedence is hard to read.
9. **`STOCK` has `raw` category in types but no rows** — production batches don't actually move raw milk in stock; there's no source of truth for "raw milk on hand" except a hardcoded `284` in the production screen.
10. **`COLLECTIONS_TODAY` is hardcoded to date `2026-05-28`** — every screen that says "today" is referring to that date, not `new Date()`.
11. **POS "Orders / stock issue" tab and Stock "movements" tab are static demo data** with no relation to the rest of the model.
12. **No drill-down from Dashboard alerts** to the underlying record (overdue customer → customer drawer; low-stock → stock row).
13. **No printable monthly statement page** — the in-drawer statement is the only view; PDF button only toasts.
14. **No receipt persistence / "receipt history" view.**
15. **`AppShell` only protects `user != null` — no fallback for unknown role.**
